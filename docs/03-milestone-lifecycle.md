# Milestone Lifecycle

> Epic → Milestone → Phase → Card → PR → Report. This is the *unit of delivery* in SDD.

---

## The hierarchy

```
Program
  └── Epic (ticketing system)                      ← Product source of truth
        └── Milestone (M<N>-<short-name>)          ← Technical source of truth
              └── Phase 1                           ← Vertically sliced, ~1 week
                    └── Card 1.1 (layer: domain)
                          └── PR 1.1
                    └── Card 1.2 (layer: data-access)
                          └── PR 1.2
                    └── Card 1.N (layer: experience)
                          └── PR 1.N
                    └── Phase 1 Report
              └── Phase 2 (same shape)
              └── ...
              └── Milestone Retrospective
        └── Next Milestone
```

---

## Sources of truth (the invariant)

| Artifact | Source of truth | Not the source of truth |
|---|---|---|
| **Product context** (scope, decisions, risks, user stories, milestone-level ACs) | Jira Epic (or your ticketing system's equivalent) | Repo markdown |
| **Per-task PRD** (10 mandatory sections) | Ticket / card | Repo markdown |
| **Technical artifacts** (implementation plan, ADRs, LLDs, phase reports) | Repo markdown at `capabilities/<capability>/docs/delivery/<milestone>/` | Confluence / wiki |
| **Coding standards** | `AGENTS.md` files + `.cursor/rules/` | Slack + tribal knowledge |
| **Durable operational lessons** | `.cursor/LEARNINGS.md` | Repeat retrospectives |

**Everything is append-only.** No destructive rewrites — instead:
- Docs: strikethrough obsolete line + `Updated <YYYY-MM-DD> (PR #<n>): <reason>` note.
- Tickets: append to `## Change Log / Clarifications` section.
- Epics: append to `## Decisions Log` section.

This is enforced by the `divergence-trigger.mdc` rule → `prd-sync` skill.

## Milestone folder structure

`capabilities/<capability>/docs/delivery/<milestone>/` contains:

```
M<N>-<short-name>/
├── implementation-plan.md            ← THE technical plan. Generated by epic-implementation-planner.
├── milestone/
│   ├── README.md                     ← Landing page for the milestone
│   ├── scope.md                      ← What's in / out
│   ├── phases.md                     ← Phase-by-phase table
│   ├── schedule.md                   ← Dates + milestones
│   ├── architecture.md               ← Milestone-level architecture (may link to LLDs)
│   └── unknowns-risks.md             ← Risk register
├── features/
│   ├── phase-1/
│   │   ├── <feature-slug-1>.md       ← Per-feature per-phase detail
│   │   └── <feature-slug-2>.md
│   ├── phase-2/
│   │   └── ...
│   └── phase-N/
├── reports/
│   ├── phase-1.md                    ← Written at phase close
│   ├── phase-2.md
│   └── ...
└── adr/                              ← Optional. Milestone-specific ADRs.
    ├── adr-001-<topic>.md
    └── ...
```

**Nothing goes in `docs/milestones/` or `docs/features/`** — those are legacy locations.

## The lifecycle in five acts

### Act 1: Epic is created (product owns)

Someone (product manager, tech lead, or client stakeholder) creates an Epic in the ticketing system with at minimum:
- Business outcome
- Scope / non-scope
- User stories or capability statements
- Known risks

**Trigger:** `epic-shared-trigger.mdc` fires when the user shares the Epic key/URL and asks for an implementation plan.

### Act 2: Implementation Plan is written (tech lead + AI owns)

**Skill:** `epic-implementation-planner`.

Steps:
1. Read the Epic. Identify gaps. Ask focused questions.
2. Append clarifications back to the Epic (append-only).
3. Decide the milestone identifier (`M<N>-<short-name>`).
4. Generate `capabilities/<capability>/docs/delivery/<milestone>/implementation-plan.md`.
5. Validate phase boundaries + demonstrable outcomes with the user.

**Output:** implementation plan committed to the repo. Milestone folder scaffolded.

### Act 3: Phase is decomposed into cards (tech lead + AI owns)

**Skill:** `phase-card-generator`.

Steps:
1. Read the implementation plan.
2. For the target phase, decompose into atomic cards — one per layer touched.
3. Confirm decomposition with the user.
4. Create cards in the ticketing system, linked to the parent Epic.
5. Wire dependencies (`Blocks` / `Is blocked by`).
6. Append card keys to the implementation plan (append-only).

**Output:** cards created in ticketing, phase feature files scaffolded.

### Act 4: Cards are implemented (dev pair + AI owns)

For each card:

1. **Expand PRD.** Skill: `ticket-prd-builder`. Fills the 10 mandatory sections.
2. **Plan the PR(s).** Skill: `layered-pr-planner`. Decides if this ticket is one PR or a stack. Uses ~400 impl line budget.
3. **Implement.** Follow TDD (`tdd-bdd-workflow` skill).
4. **Self-verify.** Skill: `pr-readiness-check`. Loop: size → ACs → tests → lint → typecheck → boundaries. Up to 3 iterations.
5. **Open PR.** One layer per PR. PR template followed.
6. **Review + merge.**

**Divergence during implementation** → `divergence-trigger.mdc` fires → `prd-sync` skill applies append-only correction.

### Act 5: Phase closes (tech lead + AI owns)

**Skill:** `phase-report-writer`.

Steps:
1. Verify all phase cards are closed in the ticketing system.
2. If cards aren't closed, ask the user how to disposition them (Carried Over / Deferred / Blocked).
3. Write `capabilities/<capability>/docs/delivery/<milestone>/reports/phase-<N>.md`.
4. Include a `## What Worked / What Did Not` section — feeds the learning loop.

**Output:** phase report committed. Next phase can start.

## The 10 mandatory sections of a ticket PRD

Enforced by `card-edit-trigger.mdc` → `ticket-prd-builder`:

1. **Product Context** — why this ticket exists in the milestone
2. **Acceptance Criteria** — testable, quantified
3. **QA Notes** — how QA will verify
4. **Engineering Context** — what already exists, what's related, gotchas
5. **Layer Impact** — which layers this ticket touches
6. **PR Plan** — one PR or a stack; layer order
7. **Validation Plan** — how the ACs are validated (unit / integration / E2E)
8. **Out Of Scope** — what's explicitly not in this ticket
9. **Open Questions** — items blocking implementation
10. **Change Log / Clarifications** — append-only history

**Implementation cannot start** when any of `Product Context`, `Acceptance Criteria`, `Layer Impact`, `PR Plan`, or `Validation Plan` is missing material information. Ask focused questions instead.

## Layer order for contract changes

When a milestone spans contract changes, PRs land in this order (adjust to your architecture):

```
domain → data-access → functions → infrastructure → feature → experience
```

Meaning: the type-level change lands first (as a stack foundation), then the layers that consume it in order. Consumers reference the merged foundation, not a WIP branch.

**Why:** each PR reviewable on its own; no circular dependencies; no half-shipped contract changes in main.

## PR size and stacking

**Cap:** ~400 implementation lines per PR (production code in the primary layer). Tests, fixtures, snapshots, config, docs are excluded from the cap.

**Measurement:** use the GitHub CLI or the GitHub MCP:

```bash
gh pr view <PR_NUMBER> --json files --jq '.files[] | "\(.additions)\t\(.deletions)\t\(.path)"'
```

Filter to production files in the primary layer; sum `additions`.

**Stack rules:**
- Each PR reviewable on its own.
- Sequential dependencies allowed; circular forbidden.
- Foundation PR (types / contracts) lands first.
- No flaky behavior between merges.

Enforced by `pr-size-and-stack.mdc` + `one-layer-per-pr.mdc`.

## Retrospective cadence

| Level | When | Artifact |
|---|---|---|
| Per phase | End of every phase (typically weekly) | `reports/phase-<N>.md` |
| Per milestone | End of every milestone (typically 4–8 weeks) | `reports/milestone-<M>.md` (or bottom of phase-N report) |
| Per learning | When a mistake repeats 2–3× or a durable lesson emerges | `.cursor/LEARNINGS.md` entry |
| Per kit | When you finish a project | Update this starter kit + push learnings back |

## Common failure modes

| Failure | Symptom | Fix |
|---|---|---|
| Milestone starts without SuperSpec sign-off | PRs get rejected for scope / architecture reasons | Enforce §Spec quality gates from `docs/01-sdd-playbook.md` |
| Phase spans too many layers | PRs pile up, phase never closes | Phase = one demonstrable outcome. If it spans 6+ cards, split into two phases |
| Cards created before implementation plan is signed off | Cards drift from plan | Only run `phase-card-generator` after implementation plan sign-off |
| Divergence silently rewrites the plan | Loss of traceability | `divergence-trigger.mdc` catches this; if you see a doc without `## Change Log`, that's a red flag |
| Phase closes without a report | Anchors for next phase are lost | `phase-end-trigger.mdc` catches this; do not skip |
| One giant PR for the whole phase | Un-reviewable | `pr-size-and-stack.mdc` catches this; split before merge |
| The ticketing system has cards not in the implementation plan | Scope creep | Every card must trace to a phase in the implementation plan; otherwise open an ADR |
